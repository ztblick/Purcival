## Project context

Purcival is a mature Python project. It runs on Windows (Zach's desktop, NVIDIA
RTX 3060) with development and CLI use on macOS as well. The codebase
currently includes:

- A persona-based assistant system; Jo is the only persona currently in active use
- A self-scheduling autonomous agent loop with trigger-based wake-ups
  and a tool-based action pipeline (built and stable)
- A tool system with permission tiers (observe, message, draft, execute) and
  built-in tools for schedule management, Google Calendar, Gmail, and Telegram
  (Telegram exists in code but is not currently operable)
- A memory system (per-persona SQLite, narrative state, structured state,
  summarization via Claude, semantic retrieval via Ollama embeddings)
- LLM integrations: **Claude, ChatGPT (OpenAI), and Ollama**, with per-call-site
  model selection across chat / summary / reasoning tasks
- Telegram bot interfaces exist historically but are not the active interface
- A test suite (~150 tests across the project)

**Active development:** the Goals dashboard — a local web app for goal/step
tracking with proactive suggestions generated by the agent loop. See
PROGRESS.md → Current focus.

Reference design docs:

- `Design/PURCIVAL_DESIGN_DOC.md` — overall system design (living)
- `Design/agent_loop_design.md` — agent loop architecture
- `Design/openai_integration_design.md` — completed OpenAI work
- `Design/dashboard_goals_design.md` — Goals dashboard design (Phase 2 dashboard skeleton next)
- `README.md` — project overview and setup

## Working with Zach

Zach is a CS teacher transitioning into software engineering. He trained in
systems programming with a Microsoft Technical Fellow. He wants to be
challenged, not validated.

How to work with him:

- **Push back.** If his reasoning is weak, say so and explain why. If a design
  has a flaw, find it and tell him. Sycophancy is a failure mode, not a
  strength.
- **Ask questions when the task is unclear.** He'd rather answer three sharp
  questions than watch you build the wrong thing.
- **Design first, implement second.** For any non-trivial work, produce a plan
  or design doc and get his review before writing production code. He
  explicitly prefers this and works this way with every AI collaborator.
- **Be direct.** No padding, no stacked caveats, no "great question!" openers.
  Get to the point.
- **Complete file deliverables.** When you produce code, give him whole files
  he can save, not patches or diffs. Inside this repo you can edit in place,
  but when surfacing a proposed change for review, paste full files.
- **Match the codebase.** snake_case, type hints where they aid clarity, prose
  docstrings on non-trivial functions, small single-purpose functions,
  composition over inheritance, swappable implementations behind interfaces.

## Workflow — every session

1. Read AGENTS.md.
2. Read PROGRESS.md.
3. Read recent commits: `git log --oneline -20`.
4. Identify the active task from PROGRESS.md → Current focus.
5. If the active task is in a **design phase**: produce or refine the design
   doc, surface open questions, then stop and request Zach's review. Do not
   write production code.
6. If the active task is in an **implementation phase**: implement per the
   approved design, run tests, update reference docs if the change makes them
   stale.
7. Update PROGRESS.md: Current focus, Recent activity, and Decisions log if
   you made any substantive decisions.
8. Commit with a descriptive message.

---

## Hard rules

1. **Design-first for non-trivial work.** Anything that touches more than one
   module, introduces a new dependency, changes a public interface, or has
   architectural implications gets a design doc reviewed by Zach before code
   is written. Small bug fixes and refactors within a single function don't
   need this gate.

2. **Tests must pass before committing.** Run the full suite. If you add
   functionality, you add tests. If you change behavior, you update tests.
   Don't paper over failures by deleting assertions.

3. **Don't modify sensitive things without explicit instruction.** API keys,
   OAuth credentials, the live SQLite databases under `data/<persona>/`, and
   the production persona configurations are sensitive. Read them as needed
   for context; don't modify them without being told to.

4. **No silent scope expansion.** If you find yourself thinking "I should also
   refactor X while I'm here," stop. Either flag it in PROGRESS.md's backlog
   and move on, or ask Zach explicitly. One thing well per session beats three
   things half-done.

5. **PROGRESS.md discipline.** Sections marked *STABLE* you don't modify. The
   "Decisions log" is append-only — add new entries, never edit prior ones.
   Update "Current focus" and "Recent activity" each session.

6. **No surprise dependencies.** Adding a new third-party library is an
   architectural decision. Propose it in a design doc or ask first; don't
   slip it in.

## Code conventions

- **Python ≥ 3.11**
- **Style:** snake_case functions and variables, PascalCase classes, type
  hints where they aid clarity, prose docstrings on non-trivial functions
- **Structure:** single-responsibility functions, swappable implementations
  behind interfaces, composition over inheritance
- **Testing:** pytest; tests live alongside the modules they cover. The
  formal `tests/` directory restructure is on the future-work list — **do
  not** do it as a side effect of other work.
- **Dependencies:** prefer the standard library; new ones need justification
  in the Decisions log
- **Logging:** match Purcival's existing patterns (discover and document on
  first session if unclear)
- **No comments-as-changelog.** Don't leave comments like "# fixed bug" or
  "# changed per Zach's request." Git history is for that.
